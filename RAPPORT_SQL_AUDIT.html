CRITICAL DELETE massif sans garde ni transaction SQL-001 ✅ CORRIGÉ Lot 1 — confirm serveur + atomic (template + test à jour)

chat/views.py:1037-1040 data_clear · :508-516 project_conversations_delete · :364-378 conversation_delete
Problème
Conversation.objects.all().delete() → DELETE FROM chat_conversation + cascades (messages, documents, attachments, usage_records, exports, scheduled_task). Aucun SELECT COUNT(*) préalable, aucune confirmation serveur, aucun backup, pas de transaction.atomic() explicite dans la vue.
Impact
Perte irréversible de tout l'historique + fichiers orphelins si post_delete échoue. Sous SQLite : cascade chargée en mémoire → verrou DB long.
Correction
-- Vérification avant :
SELECT COUNT(*) FROM chat_conversation;
SELECT COUNT(*) FROM chat_message;
-- Vue gardée :
from django.db import transaction
if request.POST.get("confirm") != "SUPPRIMER":
    messages.error(request, "Confirmation requise."); return redirect(...)
with transaction.atomic():
    Conversation.objects.all().delete()
-- Backup : copie db.sqlite3 ou .dump avant.
Répercussion
Un simple confirm JS se contourne par curl → contrôle serveur obligatoire. Ne pas mettre on_delete=PROTECT partout : casserait les suppressions légitimes. Ne toucher qu'aux vues + backup.
